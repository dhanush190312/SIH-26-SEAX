Architecture of record

SatQuery AI Architecture

An agentic vision–language assistant for satellite imagery. Upload one or two rasters, ask a question in plain English, and get an answer that cites the numbers it was derived from — plus an execution trace an assessor can audit line by line. This page is what gets served, what talks to what, and the four invariants that keep it from collapsing into a generic VLM wrapper.

ISRO / SAC challenge 3 served models · 1 fine-tune resident on one free 16 GB T4 everything served is Apache-2.0

Invariants

Four rules the code enforces, not the prompt

A generic VLM wrapper is disqualified outright, so the load-bearing part of this system is not which model answers. It is the set of properties that hold no matter what the language model decides to do.

01 · No pixels in the cloud

The router never sees imagery

Mistral classifies the task and sequences tools. The executor injects image_id from the session itself, so raster data is never a payload on a cloud API call.

02 · Structural, not prompted

The validator prunes the tool menu

Tools an input configuration cannot support are absent from the schema the router receives. Misrouting the obvious cases becomes impossible rather than unlikely.

03 · Numbers upstream

Deterministic tools feed the VLM

NDVI/NDWI, SAR dB statistics, mask areas and box coordinates go into the prompt as structured context. This is the SAR fix: never ask a VLM to read speckle — hand it numbers and ask it to explain them.

04 · One prompt surface

One model owns every sentence

Specialists emit numbers only. Every user-facing clause comes from the tuned Qwen, and the composer drops any clause with no tool output behind it — so hallucination has exactly one place to be policed.

The stack

Three served models behind a deterministic tool loop

The controller is a hand-rolled plan → execute → compose loop rather than a framework, because every hop has to be auditable. Below it, three models stay resident at once — no request ever waits for weights to be swapped in.

Lifecycle

One request, end to end

Concretely: two optical GeoTIFFs of the same district eighteen months apart, and the question “What changed between these dates, and where?” Every step writes its own entry into the trace.

  1. Validator

    Both rasters open, and the pair is compatible

    Format sniffed through rasterio, modality inferred from band count and dtype, then the pair check: matching CRS, overlapping footprints, common ground sample distance. A pair that fails here is refused with a reason rather than answered badly.

    image_a: 12 bands, uint16, EPSG:32644, 10 m GSD  → optical
image_b: 12 bands, uint16, EPSG:32644, 10 m GSD  → optical
pair:    footprint_overlap 0.98 · co_registered true · pair_type "bitemporal"
  2. Registry

    The tool menu is built for this configuration

    Because a valid bi-temporal pair exists, the change tools are registered. Because neither image is SAR, fusion is withheld — and the trace records that it was withheld, and why.

    offered:  vqa · caption · ground · indices · change/map · change/describe
withheld: fusion   ← reason: "no SAR image in pair"
  3. Router · Mistral

    A small JSON plan, produced without ever seeing a pixel

    The router receives the question, the pruned tool schema and the validation summary, all as text. It returns a plan; it does not return an answer.

    { "task":  "change_vqa",
  "tools": [ "change_map", "change_describe" ],
  "params": { "detail": "detailed" } }
  4. Executor · MCI

    The change map comes first, as evidence

    The executor injects the pair_id itself and calls the specialist. What comes back is geometry and arithmetic — no language at all.

    mask_url:         /files/q123/change_mask.png
changed_area_pct: 14.2   ·  num_regions: 7
centroid_quadrant: "north-east"  ·  largest_region_pct: 6.1
  5. Executor · Qwen

    Those numbers enter the prompt, and then the VLM speaks

    The tuned Qwen receives both images and the MCI statistics as structured context. This ordering is invariant 03 — the deterministic result constrains the sentence, not the other way round.

    POST /tools/v1/change/describe
  images:   [ image_a, image_b ]
  evidence: { changed_area_pct: 14.2, num_regions: 7, quadrant: "north-east" }
  question: "What changed between these dates, and where?"
  6. Composer

    Every clause is tied back to a tool output

    The composer assembles answer, confidence and evidence list, and drops any clause it cannot attribute. Confidence comes from generation self-consistency and the specialist's own scores — not from the model asserting a number.

    answer: "Built-up area increased by approximately 14% between the two dates,
         concentrated in the north-east quadrant."
         ├─ "approximately 14%"   ← change_map.changed_area_pct 14.2
         └─ "north-east quadrant" ← change_map.centroid_quadrant
confidence: 0.82
  7. Response

    The answer, and the receipt

    The GUI renders the overlay, the confidence panel and the full trace; the same content is written to a downloadable PDF. The trace is what gets assessed, so it is a first-class output rather than a debug log.

    GET /api/v1/queries/q123        → answer · confidence · evidence[]
GET /api/v1/queries/q123/trace  → validation · plan · tool calls · timings
GET /api/v1/queries/q123/report → PDF

Gating

Why misrouting the obvious cases is impossible

All seven tools exist in the codebase for every request. What differs is how many of them are described to the router at all — and that is decided by the validator's report, before the language model is invoked.

Budget

Why exactly three models are served

The free tier is a single 16 GB T4. Anything over that ceiling means loading and unloading weights per request — a slow demo, plus a job queue to write and debug. Collapsing six candidates to three is what buys a resident interior.

The T4 is SM75, which fixes two things everywhere in the stack: fp16 only — never bf16 — and sdpa attention, never FlashAttention-2.

Status

Where the build stands

  • landed  Phase 1 — loaders and evaluation harness. Built deliberately before any fine-tuning, because the before/after benchmark delta is the adaptation proof. numpy is the only hard dependency, and every metric is validated against an oracle predictor so a metric bug surfaces locally rather than after a five-hour Colab run.
  • landed  Phase 2 — the loop above, running. Validator, tool menu, router, executor, composer, trace, the seven tool endpoints, the web app and the PDF report. 516 tests, green on a laptop — with no GPU, no model weights and no API key, because every served slot has a deterministic backend beside its model backend and the answer always names the one that ran.

The deterministic backends measure real quantities and refuse the questions they cannot answer, so the demo is honest rather than mocked: on a synthetic scene the change detector reports 7.32% for a 7.32% change and 0.0% for an unchanged pair under an illumination shift. Counting objects, naming a land use and grounding a free-form phrase are what they say they cannot do. Two decisions changed during this build: the GUI is one self-contained HTML page served by the same FastAPI process rather than Gradio, and the phase order inverted — the app was built around empty slots so each trained model is a drop-in replacement rather than a prerequisite.

  • ahead  Phases 3–5. The single QLoRA run on the mixed RS instruction set; specialist training — MCI on LEVIR-MCI, the TerraMind head on BigEarthNet-MM; the remaining dataset adapters and the captioning metrics; then hardening. Tuned weights get promoted per slot only where the harness says evaluation actually improved.
